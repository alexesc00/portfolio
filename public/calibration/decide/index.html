Decide edits

After each tester run, the author proposes edits to each question on this screen, and the reviewer accepts or pushes back, with reasons on record. The sample shows the reviewer pushing back on Q2 after run 2, the brief's "57% to 90%" case.

Notes

  1. 1

    One record, in turns. Today the discussion happens in Slack and meetings, which an outside author isn't in.

  2. 2

    Small numbers. Every result is a count with a mark per tester, never a percentage.

  3. 3

    Attribution. The reviewer reads tester and platform causes once for the whole run, engineering answers for the platform, and the author answers for the question.

  4. 4

    Testers ≠ candidates. Production's pace catches the brief's Q4 and Q5 problem here, before candidates hit it.

  5. 5

    False comparisons. This is the brief's "57% to 90%." Q3 rose as much with no edit, so the stronger batch could explain Q2's jump.

  6. 6

    Nothing is reused. The author's prediction from run 1 is on record, so run 2 can show whether the edit worked.

  7. 7

    The author proposes, Colare decides. Pushing back needs a reason, so disagreement stays on record.

  8. 8

    Decide ends in one of two calls, so the loop has a defined end.
